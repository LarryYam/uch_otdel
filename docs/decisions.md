# Журнал решений

Короткие записи: что решили, почему и чем пожертвовали. Новое решение — новая запись внизу;
отменённое не удаляем, а помечаем «Заменено записью N».

## 1. Веб-приложение на Blazor Server

**Решение.** Веб, а не десктоп; Blazor Server.
**Почему.** Нагрузку согласуют много ролей одновременно; нет установки на каждый ПК; одна база кода;
логику на C# можно перенести из старой программы. Server, а не WebAssembly: данные и правила остаются на сервере,
быстрый старт, проще безопасность.
**Цена.** Нужен сервер; нет офлайна; на каждую открытую вкладку тратится память сервера.

## 2. Компоненты Radzen.Blazor (MIT)

**Решение.** Radzen, только бесплатные компоненты. DevExpress и другие платные наборы не используем.
**Почему.** Бесплатно для коммерческого продукта; грид с фильтрами, группировкой, редактированием, сводная таблица.
Проверено прототипом.
**Цена.** Только возможности бесплатных компонентов; дизайнер отчётов (аналог XtraReports) придётся подобрать бесплатный.

## 3. EF Core, две СУБД: SQL Server и PostgreSQL

**Решение.** EF Core; поддерживаем SQL Server и PostgreSQL с первого дня; миграции — отдельный проект на СУБД.
**Почему.** Крупные вузы со своим SQL Server; колледжи без лицензии — на бесплатном PostgreSQL.
**Цена.** Миграции создаются дважды; запросы проверяются на обеих СУБД (интеграционные тесты в CI).

## 4. Без хранимых процедур, логика в C#

**Решение.** Все правила расчёта — в Domain, запросы — LINQ.
**Почему.** Независимость от СУБД; правила проверяются юнит-тестами; их можно сверить со старой программой.
**Цена.** Формулы из процедур старой программы нужно переносить вручную.

## 5. Контекст данных на одну операцию

**Решение.** `IAppDbContextFactory`, контекст создаётся в каждом методе сервиса.
**Почему.** Особенность Blazor Server: долгоживущий контекст копит объекты и не допускает параллельных операций.

## 6. .NET 10

**Решение.** .NET 10 (LTS), Visual Studio 2026.
**Почему.** Поддержка .NET 8 и 9 заканчивается в ноябре 2026.

## 7. Часы экзамена хранятся, а не вычисляются при чтении

**Решение.** `Assignment.ExamHours` сохраняется в базе и пересчитывается при изменении студентов или признака экзамена.
**Почему.** Изменение норм не должно задним числом менять уже утверждённую нагрузку.
**Цена.** При смене норм нужна явная операция «пересчитать по новым нормам» (будет добавлена).

## 8. Дисциплина пока строкой

**Решение.** `Assignment.Discipline` — строка, справочника дисциплин пока нет.
**Почему.** Так устроен прототип; справочник появится вместе с учебными планами (РУП).

## 9. Нормы в базе, привязка к дереву детализации

**Решение.** Нормы хранятся в базе организации таблицей; условия включают учебный год. Нормы, правила деления
на подгруппы и правила потоков привязываются к дереву «подразделения → программа → дисциплина»;
из одинаковых норм применяется самая детализированная. Нормы из `appsettings.json` — только прототип.
**Почему.** Нормы различаются по организации, году, подразделению, дисциплине; в старой программе окно норм
было неструктурированным.

## 10. Учебные годы в одной базе

**Решение.** Все годы хранятся в одной базе; новый год начинается с чистого листа, справочники (подразделения,
нормы) общие. Перенос данных из прошлого года — отдельными командами, позже.
**Почему.** Нужно переключаться между годами и работать в двух годах одновременно.

## 11. Одна организация — одна база

**Решение.** Стандарт — отдельная база на организацию. Филиалы и подразделения СПО — узлы дерева подразделений,
а не отдельные организации. `OrganizationId` не вводим. Закрывает открытый вопрос о мультиарендности.
**Почему.** Так устроены установки у клиентов; облако — не в первой версии.
**Цена.** Для будущего облака — отдельная база на клиента.

## 12. Собственная авторизация в первой версии

**Решение.** Логины и пароли хранятся в базе приложения, как в старой программе. Права — на функции и действия
с областью (подразделения, программы); роли — шаблоны функций. Вход через AD/Keycloak — позже.

## 13. Полный журнал изменений и откат

**Решение.** Журнал всех изменений (кто, когда, было, стало), бессрочно. Перерасчёт выполняется сразу,
без предпросмотра; откат — к дате и времени с комментарием, по области (план, кафедра, подразделение, строка).
**Почему.** Перерасчёт в старой программе был непредсказуем; пользователю нужна возможность вернуть данные.
**Цена.** Рост объёма базы; откат по области требует хранить изменения на уровне строк.

## 14. Поручение связано со строкой плана

**Решение.** Каждое поручение хранит ссылку на строку плана (id из .plx). Изменение или удаление строки при
перезагрузке плана помечает поручение «план изменился», нагрузка автоматически не меняется.
**Почему.** Главная проблема старой программы — разрыв между планами и нагрузкой.

## 15. События онлайн — внутри процесса

**Решение.** Простая система событий: `IAppEventBus` в Application, реализация `InProcessAppEventBus` (singleton).
Открытые вкладки Blazor подписываются и показывают события в нижней панели; важное событие открывает её
принудительно. Первое событие — начало и окончание расчёта нагрузки.
**Почему.** У организации всегда один сервер приложения (интервью, ноябрь 2026), внешний брокер не нужен.
**Цена.** Если когда-нибудь понадобится несколько серверов (облако), рассылку придётся перевести на общий канал
(база или брокер); интерфейс `IAppEventBus` для этого и выделен.

## Открытые вопросы

- Имена таблиц в PostgreSQL: сейчас PascalCase в кавычках; при необходимости — snake_case для PostgreSQL.
- Бесплатный дизайнер отчётов с правкой шаблонов пользователем (отчёты — не в первой версии).
- Отображение дерева подразделений: есть ли подходящий бесплатный компонент Radzen (не проверено).
