# Архитектура

## Слои

```
            ┌──────────────────────────── Web (Blazor Server + Radzen) ───┐
            │  страницы, гриды, редакторы; Program.cs собирает всё вместе  │
            └──────────────┬───────────────────────────┬──────────────────┘
                           ▼                           ▼
              Application (сценарии)          Infrastructure (EF Core)
              WorkloadService, PlansService   AppDbContext, Configurations,
              IAppDbContext ◄─────────────────  выбор СУБД, демо-данные
                           │                           ▲
                           ▼                           │
                 Domain (правила)        Migrations.SqlServer / Migrations.PostgreSql
```

| Слой | Отвечает за | Не должен |
|---|---|---|
| Domain | сущности, формулы, ограничения | знать о базе, EF Core, интерфейсе |
| Application | сценарии: загрузить → правила → сохранить; DTO для экранов; права | знать, какая СУБД; содержать формулы |
| Infrastructure | EF Core, настройка таблиц, провайдеры, внешние сервисы | содержать бизнес-правила |
| Migrations.* | история схемы для конкретной СУБД | редактироваться вручную |
| Web | показ данных и вызов сценариев | считать нагрузку, обращаться к базе напрямую |

## Как проходит действие

Методист меняет часы лекций в гриде:

1. **Web**: грид передаёт изменённую строку `AssignmentRow` в `WorkloadService.UpdateAssignmentAsync`.
2. **Application**: открывает контекст, загружает `Assignment`, вызывает методы сущности, сохраняет,
   возвращает свежую строку.
3. **Domain**: `Assignment.SetHours` проверяет значения; `SetExam`/`SetStudents` пересчитывают часы экзамена.
4. **Infrastructure**: EF Core переводит изменения в SQL выбранной СУБД.

## Независимость от СУБД

- Провайдер выбирается настройкой `Database:Provider` (`SqlServer` или `PostgreSql`).
- Код запросов общий (LINQ), специфичного SQL и хранимых процедур нет.
- Миграции — отдельная сборка на каждую СУБД; приложение подключает обе и применяет нужную.
- Интеграционные тесты прогоняют одни и те же сценарии на обеих СУБД (CI на GitHub).
- Известные различия, которые учтены: регистр при поиске (`ToLower`), точность decimal (задана явно),
  время (UTC). Минимальная версия SQL Server — 2016: EF Core использует OPENJSON для списков значений.

## Blazor Server

- Состояние вкладки живёт на сервере, поэтому DbContext создаётся **на одну операцию**
  через `IAppDbContextFactory` и сразу закрывается.
- Страницы получают DTO и не держат сущности EF.

## Большие объёмы данных

Замеры прототипа: 300 000 строк в памяти на вкладку — 40–150 МБ и около 0,5 с на группировку при каждой
перерисовке. Поэтому:

- справочники и таблицы до десятков тысяч строк — можно грузить целиком;
- большие таблицы — серверный режим грида (`LoadData`): фильтр, сортировка, страница выполняются в базе;
- итоги и значения для фильтров — отдельные запросы (`SUM`, `DISTINCT`);
- группировка больших таблиц — строки групп с итогами из базы (`GROUP BY`) + подгрузка содержимого при раскрытии.

## Тесты

- `Domain/*` — правила, без базы.
- `Application/Scenarios.cs` — сценарии на демо-данных; выполняются в памяти (`InMemoryScenarioTests`)
  и на SQL Server и PostgreSQL (`DatabaseProviderTests`).

  (Claude или локальная модель). Инструменты — обёртки над сценариями Application; изменяющие действия
  только с подтверждением пользователя и записью в журнал. Сначала — вопросы по данным (только чтение).

- **Организации** — одна организация на базу, филиалы — узлы дерева подразделений; облако — не в первой
  версии (запись 11).
- **Права и пользователи** — собственная авторизация, права на функции с областью (запись 12).
- **Журнал изменений и откат** (запись 13).
